# PACP v0.1: Personal Agent Connection Protocol (draft)

**Status: Proposed draft.** Nothing implements PACP. No endpoints, SDKs, credentials, registries or conformance suite exist. No interoperability with any agent, vendor or protocol is claimed. All identifiers and examples are synthetic: they use the `urn:example:` namespace ([RFC 6963](https://www.rfc-editor.org/rfc/rfc6963)) and `example.com` / `example.org` hosts.

PACP is separate from OpenFleet. OpenFleet is one proposed product that would implement the coordinator side. Adapters for particular agents are separate again.

## 1. Scope

PACP proposes the **meaning** of messages between a personal agent and a coordinator that holds user-owned memory. Through those messages an agent can:

- identify itself and declare what it can do;
- act under scoped, revocable grants from the owner;
- read memory as scoped references with provenance;
- propose memory writes, with conflicts detected;
- delegate tasks and hand them off, including to downstream coding fleets;
- report status, results and uncertainty.

A user may connect a single agent and add others later. Nothing in PACP requires more than one agent.

**Not in scope for v0.1:** transport and wire bindings, authentication mechanisms, model inference, internals of coding fleets, detailed memory policy (§3), and business multiplayer (many owners or organisations).

The key words MUST, MUST NOT, SHOULD and MAY are used as in [BCP 14](https://www.rfc-editor.org/info/bcp14) ([RFC 2119](https://www.rfc-editor.org/rfc/rfc2119), [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174)). They describe this proposal only.

## 2. Roles and terms

| Term | Meaning |
| --- | --- |
| **Owner** | The person who owns the memory and issues and revokes every grant. |
| **Agent** | A personal agent instance acting through an adapter. |
| **Adapter** | Translates between one agent's supported interface and PACP. It exists only where such an interface exists and the owner may use it. |
| **Coordinator** | Implements the coordinator side of PACP: checks grants, brokers memory, routes delegation, records provenance. |
| **Fleet** | A downstream executor, such as a cloud coding fleet, reached through the coordinator. |
| **Operation** | One logical request, identified by a stable `operation_id`. |
| **Grant** | An owner-issued, scoped, expiring permission for one grantee. |

## 3. Durable memory and context windows

These are different things, and PACP keeps them apart:

| | Durable memory | Context window |
| --- | --- | --- |
| Owner | The owner | Nobody. It is a transient input to one model invocation. |
| Lifetime | Durable. The retention rules are open. | Ends with the invocation or session |
| Identity | Stable `ref` plus a `version` | None |
| Changes | Only through the coordinator's write path (§8) | Whatever the agent puts there |
| Provenance | Required on every record | Not tracked by PACP |

Rules:

1. Reading memory into a context window creates a **transient copy**. The copy carries no authority.
2. Context window contents MUST NOT become durable memory except through the coordinator's write path (§8). Automatic capture uses that path too.
3. Memory content is **data, not instructions**. A coordinator or agent MUST NOT treat text in memory, or in another agent's result, as a grant, an approval or a command.
4. **Detailed memory policy is not settled in v0.1.** Consent, conflict resolution, encryption, retention, and whether agents may keep copies are all left to a separate memory design session. PACP does not assume where memory is stored.

## 4. Message envelope

Every message carries:

| Field | Required | Meaning |
| --- | --- | --- |
| `pacp` | yes | Protocol version, such as `"0.1"` (§13) |
| `message_id` | yes | Unique for this message |
| `type` | yes | Message type, such as `memory.read` |
| `operation_id` | for requests and results | Stable across retries of one logical operation (§10) |
| `parent_operation_id` | for delegated work | The operation that caused this one |
| `traceparent` | recommended | [W3C Trace Context](https://www.w3.org/TR/trace-context/) correlation |
| `sender`, `audience` | yes | Principal identifiers (§5) |
| `sent_at` | yes | [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339) timestamp |
| `critical` | optional | Extension fields the receiver MUST understand or reject (similar to JOSE `crit`, [RFC 7515](https://www.rfc-editor.org/rfc/rfc7515#section-4.1.11)) |
| `body` | yes | Type-specific content |

The envelope could map onto [CloudEvents 1.0](https://github.com/cloudevents/spec) attributes. That mapping is an open question, not a requirement.

**Examples in this document.** The message below is the only **complete message**: it carries every required envelope field. Its `traceparent` value is the example value from the W3C Trace Context specification. Later examples are marked in one of two ways:

- **Fragment** examples show only the fields that matter to their section. They are not conforming messages; a real message would also carry every required envelope field.
- **Record** examples are stored objects, not messages.

Complete message:

```json
{
  "pacp": "0.1",
  "message_id": "urn:example:pacp:msg:0001",
  "type": "memory.read",
  "operation_id": "urn:example:pacp:op:7f3a",
  "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
  "sender": "urn:example:pacp:agent:chat-a",
  "audience": "urn:example:pacp:coordinator:home",
  "sent_at": "2026-01-15T09:00:00Z",
  "body": { "scope": "projects/example-project" }
}
```

## 5. Identity

- Every party has a stable **principal identifier**, which is a URI: owner, agent, adapter, coordinator, fleet.
- An **agent binding** ties one agent to one owner and one adapter. The coordinator MUST authenticate the binding through a mechanism defined by the transport binding, such as OAuth 2.0 client authentication ([RFC 6749](https://www.rfc-editor.org/rfc/rfc6749)) or mutual TLS. PACP v0.1 does not choose one.
- An agent's statements about itself are not identity. Display names are not identity.
- If an agent's vendor offers no way to verify its identity, the binding records `"authenticated_by": "adapter-only"`. The coordinator SHOULD restrict that agent's grants accordingly.

Record (agent binding):

```json
{
  "agent": "urn:example:pacp:agent:chat-a",
  "owner": "urn:example:pacp:owner:owner-a",
  "adapter": "urn:example:pacp:adapter:chat-a",
  "kind": "chat-assistant",
  "authenticated_by": "binding-defined",
  "bound_at": "2026-01-10T12:00:00Z"
}
```

## 6. Capabilities

An agent or fleet declares, for each message type, whether it is `supported`, `unsupported` or `unknown`. A coordinator MUST treat `unknown` the same as `unsupported`.

**A capability is not a permission.** A supported capability can still be refused for lack of a grant.

Fragment:

```json
{
  "type": "capabilities.declare",
  "body": {
    "pacp_versions": ["0.1"],
    "messages": {
      "memory.read": "supported",
      "memory.propose": "supported",
      "task.delegate": "unsupported",
      "task.handoff.accept": "unknown"
    },
    "limits": { "max_records_per_read": 50 }
  }
}
```

## 7. Authorization and revocation

- **Default deny.** With no applicable grant, the answer is `forbidden`.
- Grants are issued by the owner, scoped, purpose-bound and time-limited. Their shape follows `authorization_details` from OAuth 2.0 Rich Authorization Requests ([RFC 9396](https://www.rfc-editor.org/rfc/rfc9396)).
- Memory actions in v0.1 are `read` and `propose`. The meaning of retraction and deletion is left to the memory design session.
- The coordinator MUST check grants on **every** operation, not only when a session starts.
- **Attenuation:** a delegated grant MUST NOT exceed the delegator's own grant.
- **Bounded control:** grants and policies cannot authorise anything that provider permissions, platform restrictions or applicable safety requirements forbid. Such a request is reported as `rejected` or `unsupported`, not attempted.
- **Plan approval is not a grant.** Approving a plan does not authorise every action the plan leads to (§9).
- **Revocation** may happen at any time. The coordinator then:
  - rejects new operations under the grant;
  - stops in-flight operations at their next checkpoint and reports them as `revoked`;
  - lists the effects already committed. It does not silently undo them.
- When grants are carried as OAuth tokens, revoking the token follows [RFC 7009](https://www.rfc-editor.org/rfc/rfc7009). A revoked grant can never be used again, even if a token copy is still in circulation.

Record (grant):

```json
{
  "grant_id": "urn:example:pacp:grant:g-12",
  "owner": "urn:example:pacp:owner:owner-a",
  "grantee": "urn:example:pacp:agent:email-b",
  "authorization_details": [
    {
      "type": "pacp_memory",
      "locations": ["urn:example:pacp:coordinator:home"],
      "identifier": "projects/example-project",
      "actions": ["read", "propose"]
    }
  ],
  "purpose": "Keep project dates current",
  "not_before": "2026-01-10T12:00:00Z",
  "expires_at": "2026-02-10T12:00:00Z"
}
```

Fragment:

```json
{
  "type": "grant.revoked",
  "body": {
    "grant_id": "urn:example:pacp:grant:g-12",
    "revoked_at": "2026-01-20T08:00:00Z",
    "in_flight": [
      { "operation_id": "urn:example:pacp:op:aa01", "state": "revoked" }
    ],
    "committed_effects": ["urn:example:pacp:mem:projects/example-project/review-date#v8"]
  }
}
```

## 8. Memory references, provenance and writes

### Reading

A read returns **references** with versions and provenance, plus only the content the grant allows. Records outside the grant are neither returned nor revealed to exist.

Provenance uses [W3C PROV](https://www.w3.org/TR/prov-overview/) concepts: who the record is attributed to, which operation generated it, what it was derived from, and when.

Fragment:

```json
{
  "type": "memory.read.result",
  "operation_id": "urn:example:pacp:op:7f3a",
  "body": {
    "records": [
      {
        "ref": "urn:example:pacp:mem:projects/example-project/review-date",
        "version": "v7",
        "scope": "projects/example-project",
        "content_type": "text/plain",
        "content": "Review moved to Friday.",
        "provenance": {
          "was_attributed_to": "urn:example:pacp:agent:email-b",
          "was_generated_by": "urn:example:pacp:op:2c41",
          "was_derived_from": ["urn:example:pacp:source:message-1"],
          "generated_at": "2026-01-14T17:20:00Z",
          "accepted_by": "urn:example:pacp:policy:capture-1"
        }
      }
    ]
  }
}
```

### Writing

Agents do not change memory directly. Every write, including automatic capture, is submitted as `memory.propose` with a `base_version`. This works like an HTTP conditional request with `If-Match` ([RFC 9110 §13.1.1](https://www.rfc-editor.org/rfc/rfc9110#section-13.1.1)). The coordinator reports one of these outcomes:

| Outcome | Meaning |
| --- | --- |
| `accepted` | Applied as a new version, with provenance recorded |
| `conflict` | `base_version` is stale. Nothing changed. The current version is returned. |
| `needs_review` | Policy asks for review before the write is applied. Nothing changes until then. |
| `rejected` | Not allowed, or invalid |
| `uncertain` | The coordinator cannot tell whether the write was applied (§12) |

PACP v0.1 defines only how these outcomes are **reported**. Which writes are captured automatically, which need review, and how conflicts are resolved are left to the memory design session.

Fragment:

```json
{
  "type": "memory.propose",
  "operation_id": "urn:example:pacp:op:5b20",
  "sender": "urn:example:pacp:agent:email-b",
  "body": {
    "change": "update",
    "ref": "urn:example:pacp:mem:projects/example-project/review-date",
    "base_version": "v7",
    "content_type": "text/plain",
    "content": "Review moved to Monday.",
    "rationale": "A newer message from the organiser.",
    "derived_from": ["urn:example:pacp:source:message-2"]
  }
}
```

The response uses Problem Details ([RFC 9457](https://www.rfc-editor.org/rfc/rfc9457)) with a `pacp_code` extension member. Fragment:

```json
{
  "type": "memory.propose.result",
  "operation_id": "urn:example:pacp:op:5b20",
  "body": {
    "outcome": "conflict",
    "current_version": "v8",
    "problem": {
      "title": "Base version is stale",
      "pacp_code": "conflict",
      "detail": "The record changed after v7. Re-read before proposing again."
    }
  }
}
```

## 9. Delegation and handoff

**Delegation** asks the coordinator to have someone else do part of a task: another agent, or a fleet. The request carries:

- the task;
- input memory references;
- the authorization needed, which MUST be within the delegator's grant;
- bounds, such as an attempt limit and a deadline;
- the approved plan it belongs to, if any;
- the policy gates that apply.

The actor chain is recorded in the spirit of the `act` claim from OAuth 2.0 Token Exchange ([RFC 8693](https://www.rfc-editor.org/rfc/rfc8693#section-4.1)), so it is always clear who acted for whom.

**Handoff** transfers ownership of a task. A task has exactly one owner at a time. A handoff completes only when the recipient sends `task.handoff.accept`. Until then, the original owner keeps the task. The handoff carries a checkpoint reference and any open questions.

PACP carries requests, status and results to and from a fleet. It does not define how the fleet works inside.

**Checkpoints are policy.** The owner's policy decides which effects are gated, for example merging, publishing, spending or deleting. At a gated effect, the coordinator does one of two things:

- it requests approval (`pending_approval`); or
- it proceeds, but only under a **prior authorization** that is recorded, in force, and applicable to that exact effect.

Approving a plan is not a prior authorization for every effect the plan leads to. An agent MUST NOT create or widen an authorization for itself. No policy or authorization can exceed provider permissions, platform restrictions or applicable safety requirements (§7).

Fragment:

```json
{
  "type": "task.delegate",
  "operation_id": "urn:example:pacp:op:9d10",
  "parent_operation_id": "urn:example:pacp:op:9d00",
  "sender": "urn:example:pacp:agent:chat-a",
  "audience": "urn:example:pacp:coordinator:home",
  "body": {
    "to": "urn:example:pacp:fleet:coding",
    "on_behalf_of": "urn:example:pacp:owner:owner-a",
    "act": { "sub": "urn:example:pacp:agent:chat-a" },
    "task": "Fix the failing date-parsing test in example-repo.",
    "inputs": ["urn:example:pacp:mem:projects/example-project/review-date"],
    "authorization_details": [
      {
        "type": "pacp_repository",
        "identifier": "https://git.example.com/example/example-repo",
        "actions": ["create_branch", "open_pull_request"]
      }
    ],
    "bounds": { "max_rework_attempts": 3, "deadline": "2026-01-16T17:00:00Z" },
    "plan": "urn:example:pacp:plan:p-3",
    "plan_approval": "urn:example:pacp:approval:a-7",
    "policy_gates": [
      { "effect": "merge", "rule": "request_approval" },
      { "effect": "open_pull_request", "rule": "prior_authorization", "authorization": "urn:example:pacp:authz:z-2" }
    ]
  }
}
```

## 10. Correlation and idempotency

- `operation_id` is chosen by the client and stays the same on every retry. The coordinator deduplicates:
  - same `operation_id` and same payload: return the original outcome, with no second effect;
  - same `operation_id` and different payload: reject with `idempotency_mismatch`.

  This follows the idea of the [Idempotency-Key HTTP header draft](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/). That draft is an IETF working-group Internet-Draft, not a standard. Its latest revision, -07, expired on 2026-04-18 according to the IETF Datatracker, checked on 2026-10-22.
- `parent_operation_id` links the steps of a delegation chain. `traceparent` links them to traces.
- PACP assumes **at-least-once** delivery with idempotent handling. It does **not** promise exactly-once effects, and it cannot guarantee anything on behalf of a downstream provider.

## 11. Status and results

| State | Terminal | Meaning |
| --- | --- | --- |
| `received` | no | Recorded, not yet checked |
| `pending_approval` | no | Waiting at a policy gate for an approval |
| `accepted` | no | Admitted, not started |
| `running` | no | In progress |
| `uncertain` | no | Effect unknown. Must be reconciled (§12). |
| `succeeded` | yes | Done, with evidence |
| `failed` | yes | Did not achieve the task |
| `rejected` | yes | Refused: forbidden, invalid or out of bounds |
| `cancelled` | yes | Stopped by request |
| `revoked` | yes | Stopped because its grant was revoked |

A terminal state never changes. Each result lists its **evidence**, and each evidence item says whether the coordinator observed it directly (`observed`) or another party only reported it (`reported`). When a gated effect went ahead, the result names the approval or prior authorization that allowed it.

Fragment:

```json
{
  "type": "task.status",
  "operation_id": "urn:example:pacp:op:9d10",
  "body": {
    "state": "pending_approval",
    "attempt": 2,
    "max_attempts": 3,
    "awaiting": { "effect": "merge", "rule": "request_approval" },
    "evidence": [
      { "kind": "pull_request", "locator": "https://git.example.com/example/example-repo/pull/1", "class": "observed" },
      { "kind": "test_report", "locator": "urn:example:pacp:artifact:test-run-5", "class": "reported" }
    ],
    "updated_at": "2026-01-15T14:05:00Z"
  }
}
```

## 12. Unsupported and uncertain outcomes

- **`unsupported`**: the capability does not exist for this agent, adapter or fleet. It MUST be reported explicitly and MUST NOT be silently emulated. This is the expected answer wherever a personal agent offers no supported interface.
- **`uncertain`**: the effect may or may not have happened, for example after a timeout or a lost acknowledgement. It MUST NOT be reported as success or failure. The client MUST reconcile with `task.status.query` or `memory.read` **before** retrying, and a retry MUST reuse the same `operation_id`.

Fragment:

```json
{
  "type": "task.status",
  "operation_id": "urn:example:pacp:op:9d10",
  "body": {
    "state": "uncertain",
    "problem": {
      "title": "Start request timed out",
      "pacp_code": "effect_unknown",
      "detail": "The fleet may or may not have started work. Query status before retrying with the same operation_id."
    }
  }
}
```

## 13. Versioning

- `pacp` is `"MAJOR.MINOR"`. While the major version is 0, any draft may change incompatibly, and peers MUST match the exact version.
- From 1.0, the intent is [Semantic Versioning](https://semver.org/spec/v2.0.0.html) for the protocol: minor versions add features, and major versions break compatibility.
- Negotiation: each side declares `pacp_versions` (§6), and the highest common version is used. If there is none, the result is `unsupported_version`, listing the versions the coordinator supports.
- A receiver ignores unknown fields, unless they are listed in `critical`. In that case it rejects the message with `unsupported_extension`.

## 14. Security and privacy considerations

- **Minimise.** Return the least content that serves the purpose, and prefer references to content.
- **Sensitive scopes** (health, finances, credentials, other people's data) need special care. How they are identified and protected is a memory-design question.
- **Prompt injection.** Memory and results are untrusted data (§3 rule 3).
- **Audit.** Every grant check, write outcome, delegation and revocation is logged with provenance, so the owner can see who knew and changed what.
- **No credentials in PACP bodies.** Credentials belong to the transport binding. They never belong in memory content or task text.

## 15. Proposed conformance checks

These are **proposed checks only**. No test suite exists. Passing them would not, on its own, show interoperability with any agent or vendor.

| ID | Check | Expected |
| --- | --- | --- |
| ENV-1 | Send a message without `pacp`, `message_id`, `type` or `sender` | Rejected with `invalid_message` |
| ENV-2 | Add an unknown field, then list it in `critical` | Ignored the first time, `unsupported_extension` the second |
| ID-1 | Send from a sender with no authenticated binding | Rejected, with no effect |
| CAP-1 | Request a capability declared `unsupported` or `unknown` | `unsupported`, not emulated |
| CAP-2 | Request a supported capability without a grant | `forbidden` |
| AUTH-1 | Read with an expired grant | `forbidden` |
| AUTH-2 | Revoke a grant during a running operation | New operations `forbidden`; in-flight reaches `revoked`; committed effects listed |
| AUTH-3 | Delegate authorization broader than the delegator's grant | `rejected` |
| MEM-1 | Read a scope partly outside the grant | Only in-grant records; nothing reveals the others exist |
| MEM-2 | Inspect any returned record | Has `ref`, `version` and `provenance` |
| MEM-3 | Try every message type other than `memory.propose` to change memory | Memory unchanged |
| WRITE-1 | Propose with a stale `base_version` | `conflict`; record unchanged; current version returned |
| WRITE-2 | Propose a valid write | New version; provenance names the agent, operation and sources |
| WRITE-3 | Propose a write that policy marks for review | `needs_review`; unchanged until reviewed |
| AUTH-4 | Request an effect that a provider permission or platform restriction forbids | `rejected` or `unsupported`; not attempted |
| DEL-1 | Delegate a task | Child operation has `parent_operation_id` and an actor chain |
| DEL-2 | Hand off without the recipient accepting | The original owner still owns the task |
| DEL-3 | Reach a gated effect with no approval and no applicable prior authorization | Never `succeeded`; stays `pending_approval` |
| DEL-4 | Offer only a plan approval for a gated effect | Treated as no authorization; stays `pending_approval` |
| DEL-5 | Have an agent create or widen its own authorization | `rejected` |
| IDEM-1 | Replay the same operation with the same payload | Same outcome, no duplicate effect |
| IDEM-2 | Reuse an `operation_id` with a different payload | `idempotency_mismatch` |
| IDEM-3 | Drop the acknowledgement of a start request | `uncertain` until reconciled, with no blind retry |
| STAT-1 | Send updates after a terminal state | Terminal state unchanged |
| STAT-2 | Inspect a result's evidence | Every item marked `observed` or `reported` |
| STAT-3 | Inspect the result of a gated effect that went ahead | Names the approval or prior authorization used |
| VER-1 | Negotiate with no common version | `unsupported_version`, listing the coordinator's versions |

## 16. Related work

PACP should reuse rather than compete wherever possible. It may become a profile or extension of an existing protocol instead of a separate one. That is an open question.

- [Model Context Protocol](https://modelcontextprotocol.io/) connects models and agents to tools and data.
- [Agent2Agent (A2A)](https://a2a-protocol.org/) covers communication between agents.
- The standards cited above: OAuth 2.0 and its extensions (RFC 6749, 7009, 8693, 9396), RFC 9110 conditional requests, RFC 9457 Problem Details, W3C Trace Context, W3C PROV and CloudEvents.

No compatibility with any of these is claimed.

## 17. Open questions

1. Transport binding: HTTP plus JSON, a profile of MCP or A2A, or several.
2. The identity and authentication mechanism, especially for agents whose vendors offer no attestation.
3. Memory behaviour, left to a separate design session: consent, conflict resolution, encryption, retention, retraction and deletion, and sensitivity labels.
4. The memory record schema and content types.
5. How policy gates and prior authorizations are expressed, and how they expire.
6. Offline and local-first operation.
7. Whether PACP should move to its own repository with its own governance.
